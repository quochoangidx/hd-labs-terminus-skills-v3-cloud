Our incident response team collects the same evidence from every Linux host it suspects was broken into over SSH: the rotated auth logs, the binary wtmp and btmp login records, the users' shell histories and authorized_keys files, the package manager's log and file lists, and a listing of every path on the host with its mtime and ctime. We want this triage in forensics done by a program instead of by hand. Write `/app/triage.py`, run as `python3 /app/triage.py <evidence_dir> <out.json>`, that reads one evidence directory and writes the incident report for it: where and when the attacker first got in (account, source address and UTC time), the attacker's source addresses and accounts, when they escalated to root, which persistence artefacts they left, and their first and last activity. The case-handling guide `/app/docs/case-guide.md` is the authority for how the team reads this evidence, `/app/docs/record-formats.md` describes the directory layout and every record format, and `/app/docs/report.md` fixes the JSON report. The existing `/app/triage.py` only parses its arguments and writes an empty report.

`/app/evidence/case-1` is one real-shaped collection you can develop against; no report is supplied for it. Your program will be run, with no network, as an unprivileged user and read-only evidence, on case-1 and on many other evidence directories collected the same way from other hosts, and each report is compared field by field with the report the guide gives, the three list fields compared as sets. Every rule in the guide holds for every such directory, not only for the example case. Use only the Python standard library; keep the program in `/app/triage.py` (it may read files under `/app/docs`, but it must not depend on anything in `/app/evidence`).

The other hosts differ in everything the guide lets vary: host names, account names and addresses; UTC offsets from -12:00 to +14:00 in quarter hours; years from 2019 to 2031, including collections that cross from December into January; one to six auth-log files, some of whose oldest lines were rotated away; with or without one clock step of 30 to 7,200 seconds; up to three weeks of evidence with up to a few thousand auth-log lines, failed attempts from scanners and from users who mistype, administrators logging in with keys and using sudo while the attacker is on the host, histories with and without timestamps, package installations at any time, and files whose mtime says something other than their ctime.
