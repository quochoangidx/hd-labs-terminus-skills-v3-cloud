Our minimal images ship without `sed`, and the scripts that still call it are being pointed at `/app/pysed/sed.py` instead. Implement it so that `python3 /app/pysed/sed.py ARGS...` behaves exactly like GNU sed 4.9 run as `sed ARGS...` with `LC_ALL=C`: the same standard output, byte for byte, and the same exit status. What goes to standard error is not compared. The GNU sed 4.9 manual is in `/app/docs/sed.txt`.

It has to cover this part of GNU sed:

- the options `-n`, `-E` and `-s`, each given as its own argument before the script, and scripts given with `-e SCRIPT` (repeatable, the pieces joined by newlines) or as the first non-option argument, followed by the names of input files, or none to read standard input;
- every command in chapter 3 of the manual except `e`, `F`, `r`, `R`, `w`, `W` and `v`, with every `s` flag except `e` and `w`, including the one-line and multi-line forms of `a`, `i` and `c`, labels, blocks, `!`, comments and a script whose first two characters are `#n`. Before adding each character's escaped form, `l` ends the output line with `\` if the addition would put more than N-1 characters on it, where N is the wrap length (70 unless given; 0 never wraps), and the character lists of `y` understand the escapes of section 5.8 such as `\n` and `\t`;
- every address form in chapter 4, including `first~step`, `addr1,+N`, `addr1,~N` and `0,/regexp/`;
- the regular expressions of chapter 5, basic and extended, with the GNU extensions, escapes, character classes, bracket expressions (in the C locale an equivalence class `[=c=]` matches just c) and back-references (which the `I` modifier also makes case-insensitive), the numeric escapes `\dNNN`, `\oNNN` and `\xHH` (wherever they appear, each reads as many digits of its base as are there, up to three, three and two), and the special replacement escapes `\L`, `\U`, `\l`, `\u` and `\E`. Matching is POSIX leftmost-longest: of the matches that start at the leftmost possible position, the longest one wins, whichever alternative of a `|` produces it, whatever the manual's section on `\|` suggests. When several ways of matching give that same text, which parts the groups capture is not checked.

Scripts never fail and always finish. Input is at most a few dozen lines of ASCII text, each ending with a newline; files may be empty, and a file named on the command line may not exist. Nothing sets `POSIXLY_CORRECT`. Each run has to finish within five seconds.

It will be checked against GNU sed 4.9 itself with over a thousand scripts and inputs, from one-line substitutions to multi-line scripts that juggle the hold space, over standard input and several files. Every check relies only on behaviour that the manual describes, together with the rules above. Where GNU sed 4.9 itself departs from its manual, nothing is checked; the known places are a second `*` right after a repetition in a basic regular expression, `^` or `$` in the middle of an extended one, ``\` `` and `\'` in an address with the `M` modifier, a backslash right after the whitespace of a one-line `a`, `i` or `c`, and a `c` whose range is still open when the input ends.
