Our minimal target images ship without `sed`, and the scripts that still call it are being pointed at `/app/pysed/sed.py` instead. This development image still has GNU sed 4.9 as `/bin/sed`, so you can compare against it while you work, but the program itself may not call it. Implement it so that `python3 /app/pysed/sed.py ARGS...` behaves exactly like GNU sed 4.9 run as `sed ARGS...` with `LC_ALL=C`: the same standard output, byte for byte, and the same exit status. What goes to standard error is not compared.

The GNU sed 4.9 manual is in `/app/docs/sed.txt`. `/app/docs/scope.md` lists the part of it the program has to cover: the options, commands, address forms and regular-expression features that are used, the points the manual leaves open and how GNU sed 4.9 settles them, and the places where the binary departs from its manual, which are left open.

Scripts never fail and always finish. Input is at most a few dozen lines of ASCII text, each ending with a newline; files may be empty, and a file named on the command line may not exist. Nothing sets `POSIXLY_CORRECT`. Each run has to finish within five seconds.

The editing has to be done in Python itself: the program may not start other processes or programs or load native code, whether through `ctypes` or as an extension module from outside Python's own standard library, and nothing under `/app` may be a compiled executable or shared library. The checks run it under a Python audit hook that ends it as soon as it tries. Python's standard library, `re` included, is fine, and Python's own `__pycache__` bytecode does not count; only `/app` is carried over to the checks, so packages installed anywhere else are not available.

It will be checked against GNU sed 4.9 itself with about twelve hundred scripts and inputs, from one-line substitutions to multi-line scripts that juggle the hold space, over standard input and several files. Every check relies only on behaviour that the manual describes, together with the rules above and in `/app/docs/scope.md`.
